# 技能推荐链路 · 流程概览

| 项目 | 内容 |
|---|---|
| 版本 | v2.0 |
| 日期 | 2026-10-13 |
| 定位 | 链路总览：这条推荐链路大致怎么跑 |

---

## 1. 要解决什么

**目标**：给定一个含 N 个技能的技能库，输入一段自然语言请求，输出最合适的 top-k 技能；当没有任何技能适合时，输出「无匹配」。

**硬约束**：

1. **不训练任何模型** —— 只使用预训练模型 / 现成 API。
2. **当天可跑通** —— 先交付可用版本，再谈优化。
3. **精排使用 Jev**（TypeSafe SystemOne）。

**非目标**：技能的实际执行编排、权限体系、前端 UI。

---

## 2. 总体思路：一个三层漏斗

```
                      用户请求 (自然语言)
                            │
             ┌──────────────┴──────────────┐
             │  第 1 层  召回 Recall        │  N  →  N′ (约 30)
             │  检索算法，不做判断          │
             └──────────────┬──────────────┘
                            │  候选技能
             ┌──────────────┴──────────────┐
             │  第 2 层  精排 Rerank        │  N′ → 概率
             │  Jev 并行判断相关度          │
             └──────────────┬──────────────┘
                            │  {技能: 概率}
             ┌──────────────┴──────────────┐
             │  第 3 层  决策 Decide        │  概率 → 结果
             │  排序 / 阈值 / 拒答 / 截断   │
             └──────────────┬──────────────┘
                            │
                  top-k 技能  或  「无匹配」
```

**贯穿全链路的原则**：

> **廉价且确定的步骤在前（把候选收窄），昂贵且非确定的模型在后（只做最后一小步判断）。**
> 模型只负责「判断相关度」，排序、阈值、截断、执行全部由代码负责。

---

## 3. 时间线上的三个阶段

分界点是「用户请求到达」。重活必须提前做，在线只跑轻活。

| 阶段 | 时机 | 做什么 | 延迟要求 |
|---|---|---|---|
| **离线** | 请求**之前** | 拉取技能、解析元数据、生成向量、建倒排 / 向量索引 | 可批量、可重跑 |
| **存储** | 常驻 | 保存「源」（技能文件）与「派生索引」 | — |
| **在线** | 请求**之时** | 召回 → 精排 → 决策 | 敏感（目标 < 1s） |

**为什么要分**：① 在线延迟预算有限，重活必须提前做；② 离线算一次 vs 在线算 N 次；③ 全库建索引在线根本来不及。

## 4. 技能从哪来

**唯一来源：ClawHub 自动下载。** 它是 OpenClaw 的公共技能注册中心，**读取与下载都不需要 token**，脚本可以直接拉；跑通链路需要一批规模和描述质量都可控的技能，所以不手写技能，也不依赖机器上已有的技能。

| 来源 | 是否采用 | 说明 |
|---|---|---|
| **ClawHub（自动下载）** | **主路径** | 调列表接口取清单（按下载量排序）→ 逐个下载技能包 |
| 本地目录 | 读取 | 下载的落地位置，也是链路的实际输入 |
| 手写自建 | 不采用 | 保证技能来源单一、可比 |

**下载流程**：

| 环节 | 做什么 |
|---|---|
| 搜索 / 筛选 | 按关键词或分类批量搜，挑出要跑的技能 |
| 下载 / 落盘 | 拉取 `SKILL.md` 与附属文件，落到本地 `skills/` 目录 |
| 记录来源 | 留下 slug、名称、版本、安装时间、来源市场，便于追溯 |
| 人工审查 | 下载后逐个过一遍再启用（见 4.1） |
| 入库 | 本地 `skills/` 目录即离线阶段的输入，从这里解析元数据、建索引 |

**下载规模**：要跑通的是完整链路，所以批次不能太小 —— **技能数量过少时召回层会被直接跳过**，链路实际只跑了精排和决策两层，看不出检索到底有没有用。

**技能的本质**：一个文件夹 + 一个 `SKILL.md`。

```
my-skill/
├── SKILL.md          # 必需：YAML frontmatter(name/description) + Markdown 指令正文
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：按需加载的文档
└── assets/           # 可选：模板 / 图标
```

> **`name` 与 `description` 是整条链路唯一的关键输入** —— 召回与精排都只吃这两项。**描述质量决定系统上限**（垃圾进垃圾出）。

### 4.1 批量下载的安全要求（必做）

市场里的技能是**不可信输入**，官方明确警告存在提示词注入、越权访问、后门程序风险。批量自动化下载会把这类风险同时放大 N 倍，因此：

1. **安装前审查** `SKILL.md` 与 `scripts/` —— 重点看有无外部网络请求、文件读写、凭据读取；
2. **记录来源与版本** —— 任何一条技能都能追溯到下载时点与来源；
3. **默认不启用** —— 人工确认后才开。

## 5. 存什么：源与索引要分开

不要把「技能库」和「向量数据库」混为一谈。

| | 存什么 | 特征 |
|---|---|---|
| **源 source** | 技能本身（name / description / 正文 / 脚本） | 人可读、可版本管理，**是真相来源** |
| **索引 derived** | 向量 + 倒排 | **派生数据，随时可从源重建** |

**演进**：起步阶段索引放进程内内存即可，重启重建；N 增长到上千后再接持久化向量库。**N 未到数千之前，不需要引入向量数据库。**

## 6. 三层各自的职责

### 6.1 第 1 层 · 召回：把 N 收窄到 N′

**做什么**：把全库候选缩小到 N′ 量级，**宁多勿漏**，优先保住召回率。这一层全是检索算法，不涉及任何模型判断。

**两路并行，再融合**：

| 通道 | 抓什么 |
|---|---|
| 稀疏（BM25） | 精确术语、技能名 |
| 稠密（向量） | 同义表达、换个说法 |
| 融合（RRF） | 只吃名次，天然免疫两路量纲差异 |

**为什么不需要训练**：向量召回用的是预训练模型的**推理调用** —— 离线对每条技能的 `name + description` 求一次向量，在线对 query 求一次向量，再算余弦相似度排序。BM25 连模型都不用，是纯词频算法。训练发生在模型厂商侧。

**规模自适应**：候选数很少时，检索这一层直接跳过，全库直接进精排。同一套代码覆盖小库和大库，不必为小库单独设计。

### 6.2 第 2 层 · 精排：让模型只做「相关度判断」

**做什么**：对 N′ 个候选，给出每条「它是完成该请求的合适技能」的概率。**只判断，不排序。**

**为什么用 Jev**：SystemOne 处理的是「给定一段状态 + 若干问题 → 答案或概率」。**一次请求可以挂多个问题**，服务端并行求值。因此正确姿势是把整批候选一次性送进去，一次拿回一组概率。

**必须避免的做法**：逐个候选单独发请求。这是整条链路上最贵的错误，会把延迟拉高一个数量级。

**边界**：模型不生成文本、不做算术、不处理图像；训练以英文为主，中文效果需自行验证。

### 6.3 第 3 层 · 决策：用代码拍板

**做什么**：把模型给的概率变成最终结果。这一步全是代码逻辑，不含任何模型判断。

```
候选 + 概率
  ├─ 1. 按概率降序排序
  ├─ 2. 过滤掉低于阈值的
  ├─ 3. 若结果为空 → 返回「无匹配」
  └─ 4. 截断到 top-k
```

**两条底线**：

- **拒答是必须的出口**。没有拒答能力的推荐系统一定会「硬凑」。
- **精排不可用时要降级**，退化为按召回顺序返回，**不能误判成拒答**。

## 7. 已知风险与局限

| 风险 | 说明 | 缓解 |
|---|---|---|
| 描述质量差 | 召回与精排同时失效 | 把 `description` 写成「做什么 + 何时用 + 触发词」，收益大于调参 |
| 阈值不当 | 过高→拒答过多；过低→硬凑 | 必须用真实数据与标注集标定，不照抄默认值 |
| 第三方技能不可信 | 提示词注入 / 越权 / 后门 | 安装前审查，默认不启用 |
| Jev 中文效果未知 | 官方以英文为主 | 用中文样本自行验证置信度与错误模式 |
| 单点依赖 Jev | 服务不可用则精排失效 | 保留可替换的降级判断器 |
| 规模增长 | N 上千后内存索引吃力 | 届时接入持久化向量库 |
| 没有评估 | 所有调优都是拍脑袋 | 建标注集；先看召回有没有漏掉正解，再看端到端排得够不够前 |

## 附：一句话总结

> **技能是文件，索引是派生数据，召回用检索（零训练），精排用 Jev（只判断），排序与阈值用代码。**
> 全链路不需要训练任何模型 —— **建模的是厂商，检索的是算法，判断的是 Jev，拍板的是你的代码。**
