| 项目 | 内容 |
|---|---|
| 版本 | v1.0 |
| 日期 | 2026-10-13 |

| 相关文件 | `skill_router.py`（同目录，参考实现） |

---

## 1. 目标与范围

**目标**：给定一个含 N 个技能的技能库，输入一段自然语言请求，输出最合适的 top-k 技能；当没有任何技能适合时，输出「无匹配」。

**硬约束**：

1. **不训练任何模型** —— 只使用预训练模型 / 现成 API。
2. **当天可跑通** —— 先交付可用版本，再谈优化。
3. **精排使用 Jev**（TypeSafe SystemOne）。

**非目标**：技能的实际执行编排、权限体系、前端 UI。

---

## 2. 总体架构：一个三层漏斗

```
                       用户请求 (自然语言)
                             │
              ┌──────────────┴──────────────┐
              │  第 1 层  召回 Recall        │  确定性 / 检索   N  →  N′ (≈30)
              │  BM25 + 向量 → RRF 融合      │
              └──────────────┬──────────────┘
                             │  候选技能 (含描述)
              ┌──────────────┴──────────────┐
              │  第 2 层  精排 Rerank        │  模型（Jev）     N′ → 概率
              │  N 个 Noul 并行 → 相关概率    │
              └──────────────┬──────────────┘
                             │  {技能: 概率}
              ┌──────────────┴──────────────┐
              │  第 3 层  决策 Decide        │  确定性 / 代码   概率 → top-k / 拒答
              │  排序 → 阈值 → 拒答 → 截断    │
              └──────────────┬──────────────┘
                             │
                   top-k 技能  或  「无匹配」
```

**贯穿性原则**：

> **廉价且确定的步骤在前（把候选收窄），昂贵且非确定的模型在后（只做最后一小步判断）。**
> 模型只负责「判断相关度」，排序、阈值、截断、执行全部由代码负责。

---

## 3. 数据流：离线 / 存储 / 在线

分界点是「用户请求到达」。

| 阶段 | 时机 | 做什么 | 延迟要求 |
|---|---|---|---|
| **离线** | 请求**之前** | 拉取技能、解析元数据、生成 embedding、建倒排/向量索引 | 不敏感，可批量可重跑 |
| **存储** | 常驻 | 保存"源"（技能文件）与"派生索引" | — |
| **在线** | 请求**之时** | 召回 → 精排 → 决策 | 敏感（目标 < 1s） |

**为什么要分**：① 延迟预算有限，重活必须提前做；② 离线算一次 vs 在线算 N 次；③ 全库建索引在线根本来不及。

## 4. Skill 从哪来

| 来源 | 位置 | 获取方式 | 状态 |
|---|---|---|---|
| **本地目录** | `~/.workbuddy/skills/`、项目级 `.workbuddy/skills/`、插件目录 | 直接读目录 | 已验证存在 |
| **Hub（自动化下载）** | SkillHub（`lightmake.site`）、ClawHub、Vercel skills、TypeSafe skills | 调搜索 API → 下载安装 | 待接入 |
| **自建** | 任意新目录 | 手写 `SKILL.md` | 支持 |

**Skill 的本质**：一个文件夹 + 一个 `SKILL.md`。

```
my-skill/
├── SKILL.md          # 必需：YAML frontmatter(name/description) + Markdown 指令正文
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：按需加载的文档
└── assets/           # 可选：模板 / 图标
```

> **`name` 与 `description` 是整条链路的关键输入** —— 召回与精排都只吃这两项。**描述质量决定系统上限**（垃圾进垃圾出）。

### 4.1 自动化下载的安全要求（必做）

Hub 上第三方技能是不可信输入，官方明确警告存在**提示词注入、越权访问、后门程序**风险。自动化批量下载时必须：

1. 安装前审查 `SKILL.md` 与其 `scripts/`；
2. 记录来源与版本，便于追溯；
3. 默认**不启用**，人工确认后再开。

## 5. 存储形态：源 vs 索引

**必须区分两层，不要把「技能库」和「向量数据库」混为一谈。**

| | 存什么 | 形式 | 特征 |
|---|---|---|---|
| **源 source** | 技能本身（name / description / 正文 / 脚本） | 文件（`skills/` 目录）或 JSON | 人可读、可 git 管理、**是真相来源** |
| **索引 derived** | 向量 + 倒排 | 内存 / 向量库 / 搜索引擎 | **派生数据，随时可从源重建** |

**演进路径**（按规模）：

| 阶段 | 索引存放 | 适用 |
|---|---|---|
| 起步 | **进程内内存**（当前实现） | N ≤ 数千，重启重建 |
| 进阶 | Chroma（最省事） / FAISS（最轻） | 需要持久化、避免重复编码 |
| 生产 | Milvus / Qdrant / pgvector + Elasticsearch / SQLite FTS5 | 大规模、需要并发与增量更新 |

> 当前 `skill_router.py` 使用**进程内内存索引**，重启即重建。**在 N 未到数千之前，不需要引入向量数据库。**

## 6. 第 1 层：召回

**职责**：把 N 缩小到 N′（默认 30），**宁多勿漏**（保召回率）。此层全部是确定性/检索算法，**不涉及训练**。

### 6.1 两路召回 + 融合

| 通道 | 实现 | 抓什么 |
|---|---|---|
| 稀疏（BM25） | 纯 Python 实现（已实现），或 SQLite FTS5 / `bm25s` | 精确术语、技能名 |
| 稠密（向量） | 预训练 embedding 模型 + 余弦相似度 | 同义表达、换个说法 |
| 融合 | **RRF**（Reciprocal Rank Fusion） | 只吃名次，天然免疫量纲差异 |

### 6.2 关键点：零训练

**向量召回不需要训练模型。**

- 用**预训练** embedding 模型：API（`text-embedding-3-small` / 通义 / Jina / Voyage）或本地（`sentence-transformers` + `BGE-M3`）。
- 流程 = 纯代码：
  ```
  离线：对每条技能的 "name + description" 调 embedding → 存向量
  在线：对 query 调 embedding → 算余弦相似度 → 排序取 top-N
  ```
- **训练发生在模型厂商侧**，本项目只做推理调用。
- BM25 甚至**连模型都不用**（纯词频算法）。

### 6.3 规模自适应

| N | 召回策略 |
|---|---|
| ≤ `SMALL_N`（默认 60） | **退化为全量**：所有技能直接进精排，跳过检索 |
| > `SMALL_N` | 走 BM25(+向量) → RRF → top-N′ |

> 同一个代码路径适配两种规模，无需两套架构。

## 7. 第 2 层：精排（Jev）

**职责**：对 N′ 个候选，给出每条「它是完成该请求的合适技能」的概率。**只判断，不排序。**

### 7.1 接口契约（已核实自官方文档）

```
POST https://api.typesafe.ai/v1/systemone
Authorization: Bearer $TYPESAFE_API_KEY
Content-Type: application/json

{
  "model": "jev-latest",              // 别名会漂移；生产固定 "jev-1.13.0"
  "state": "<文本 或 结构化对象>",
  "questions": {
    "<qid>": { "type": "noul",   "instructions": "<整句话写这里>" },
    "<qid>": { "type": "choice", "instructions": "...", "criteria": {"k": "描述"} },
    "<qid>": { "type": "score",  "instructions": "...", "criteria": ["低","中","高"] }
  }
}
```

响应：

```json
{
  "model": "jev-1.13.0",
  "answers": {
    "<qid>": { "type": "noul", "noul": 0.83 },
    "<qid>": { "type": "choice", "choice": "k", "probabilities": {...}, "confidence": 0.91 },
    "<qid>": { "type": "score", "score": 0.67, "legend": {...} }
  },
  "usage": { "input_tokens": 428, "output_tokens": 73 }
}
```

### 7.2 用于技能精排的正确写法（关键）

```python
state = {
    "query": query,
    "candidates": [{"id": c_id, "desc": c_desc}, ...],   # 整个候选数组放进 state
}
questions = {
    f"cand_{i}": {
        "type": "noul",
        "instructions": f"技能 `candidates[{i}]` 是否是完成用户请求 `query` 的合适选择？",
    }
    for i in range(len(candidates))
}
# → 一次请求，N 个 Noul 在服务端并行求值，返回 N 个概率
```

### 7.3 四条必须遵守的规则

1. **问题 ID 不会传给模型** —— 整句话必须写进 `instructions`。
2. **用反引号标注 `state` 的字段路径**（如 `` `candidates[0]` ``）。
3. **一次请求塞多个问题** —— 服务端并行求值，边际成本≈0。
   ⚠️ **绝不逐候选发请求**：这是"最贵的错误"，实测逐候选调用会把 P50 拉到 ≈2 秒。
4. **候选过多时按上下文分批**（64K 上限，约 32K 给 state）—— 分批并发。

### 7.4 调用方式与降级

| 方式 | 说明 |
|---|---|
| 官方 Python SDK | `pip install typesafe-sdk`（Python ≥ 3.10） |
| 官方 JS SDK | `npm install @typesafe-ai/sdk`（Node ≥ 20） |
| **裸 HTTP**（当前实现） | 标准库 `urllib`，零依赖 |

**降级策略**（保证链路任何情况下可跑通）：

| 情形 | 行为 |
|---|---|
| 有 `TYPESAFE_API_KEY` | 走真实 Jev |
| 无 key，有 `OPENAI_API_KEY` | `LLMJudgeProxy`：用 LLM 模拟同一 noul 接口，返回 `{id: 概率}`，**第 3 层代码无需改动** |
| 两者都没有 / `MOCK_JUDGE=1` | `MockJudge`：本地词重叠折算概率，仅用于验证链路 |

### 7.5 Jev 的已知局限

- 不生成文本、不做算术、不处理图像；
- **英文为主要训练语言**，中文效果需自行验证；
- 别名 `jev-latest` 会随版本漂移 → 生产固定版本号，并记录响应中的 `model` 字段。

## 8. 第 3 层：决策（确定性代码）

**职责**：把模型给的概率变成最终结果。全部是代码逻辑，**不涉及任何模型判断**。

```
输入: candidates[], scores{id: prob}
  │
  ├─ 1. 按 prob 降序排序
  ├─ 2. 过滤 prob < MIN_SCORE
  ├─ 3. 若结果为空 → abstain = true（返回"无匹配"）
  └─ 4. 截断 top-k（k 可为 1，也支持 k>1）
```

- **精排完全不可用时**（无任何 key）→ 退化为召回顺序返回（`mode: recall-only`），**不能误判为拒答**。
- **拒答是必须的出口**：没有拒答能力的推荐系统一定会"硬凑"。

## 9. 关键设计决策（ADR）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **不做技能分类，跳过类目** | 类目是有损瓶颈：把丰富描述压成单薄标签，再拿更弱的信号匹配。下游是会读自由文本的模型，分类这一步没有必要 |
| D2 | **索引对象是 `description` 原文**（或向量），不是类目标签 | 向量是**保信息降维**，标签是**丢信息归类** |
| D3 | **零训练** | 预训练模型 zero-shot 已够用；训练是真正做不到也不需要做的事 |
| D4 | **模型只判断，代码排序** | 判断是"开放→开放"的语义问题，适合模型；排序/阈值/IO/权限是执行问题，必须确定 |
| D5 | **必须有拒答出口** | 否则必然硬凑；阈值需在真实数据上调 |
| D6 | **小 N 时召回层退化为全量** | 同一套代码覆盖两种规模，避免为小库过度设计 |
| D7 | **混合检索（BM25 + 向量）** | 向量抓同义，BM25 抓精确术语，单用任一路都会漏 |
| D8 | **不引入向量数据库（起步阶段）** | N 未到数千时，内存/BM25 足够；避免部署复杂度 |

## 10. 工程实现现状

参考实现：同目录下的 **`skill_router.py`**（单文件，零强制依赖）。

### 10.1 模块结构

| 层 | 组件 | 说明 |
|---|---|---|
| 0 | `load_skills()` / `parse_skill_md()` | 读 `SKILL.md` 目录或 `skills.json`；无 pyyaml 时有极简解析回退 |
| 1 | `BM25` / `DenseRecall` / `rrf()` | 纯 Python BM25（中英混排分词）+ 可选向量 + RRF 融合 |
| 2 | `JevJudge` / `LLMJudgeProxy` / `MockJudge` | Jev 批量 Noul（分片+并发）/ 降级代理 / 本地模拟 |
| 3 | `decide()` | 排序 → 阈值 → 拒答 → 截断 |
| — | `evaluate()` | Recall@k + MRR |

### 10.2 关键环境变量

| 变量 | 默认 | 作用 |
|---|---|---|
| `TYPESAFE_API_KEY` | — | Jev 精排 |
| `JEV_MODEL` | `jev-latest` | 生产建议改为 `jev-1.13.0` |
| `JEV_BATCH` | 40 | 单次请求最多几个候选 |
| `SMALL_N` | 60 | ≤ 此值直接全量进精排 |
| `RECALL_K` | 30 | 召回条数 |
| `TOP_K` | 3 | 最终推荐条数 |
| `MIN_SCORE` | 0.35 | 拒答阈值（**必须在真实 Jev 上调**） |
| `USE_EMBED` | 0 | 开启稠密召回（需 `OPENAI_API_KEY`） |
| `MOCK_JUDGE` | 0 | 本地模拟判断器，零 key 验证全链路 |

### 10.3 已验证的分支

| 场景 | 结果 |
|---|---|
| 无 key | 正确降级为 `recall-only`，不报错 |
| `MOCK_JUDGE=1` | 三层跑通，排序 + 阈值过滤正确 |
| `SMALL_N=3` | 走 BM25 召回分支；弱候选被阈值滤除 |
| `MIN_SCORE=0.99` | 正确触发 `abstain` |
| `py_compile` | 语法通过 |

### 10.4 用法

```bash
# 零 key 验证链路
MOCK_JUDGE=1 python skill_router.py --demo

# 接真实技能库
export TYPESAFE_API_KEY=xxx
python skill_router.py --skills ./skills --query "帮我把简历压到一页"

# 评估
python skill_router.py --skills ./skills --eval eval.jsonl
```

## 11. 评估方案

**没有评估，所有调优都是拍脑袋。**

1. **标注集**：一批 `(query → 正确技能 id)` 对，`eval.jsonl` 每行一条，起步 30~50 条即可。
2. **两级指标**（用来定位问题出在哪一层）：
   - `Recall@RECALL_K` —— **召回闸门**：正解有没有进候选池。漏了就彻底没戏。
   - `Recall@TOP_K` / `MRR` —— **端到端**：最终结果里有没有、排得够不够前。
   - 若"召回闸门高、端到端低" → 问题在精排阈值；反之 → 问题在召回。
3. **阈值标定**：`MIN_SCORE` 必须用真实 Jev + 标注数据调。
   ⚠️ 参考教训：某实验用 0.5 阈值提升了 top-5 精确率，但**误杀 18.8% 的正确文档**。对"漏掉正确答案"的容忍度决定阈值。

## 12. 风险与局限

| 风险 | 说明 | 缓解 |
|---|---|---|
| 描述质量差 | 召回与精排同时失效 | 把 `description` 写成"做什么 + 何时用 + 触发词"；收益大于调参 |
| 阈值不当 | 过高→拒答过多；过低→硬凑 | 用标注集标定，不照抄默认值 |
| 第三方技能不可信 | 提示词注入 / 越权 / 后门 | 安装前审查；默认不启用 |
| Jev 中文效果未知 | 官方以英文为主 | 用自己的中文样本验证置信度与错误模式 |
| 单点依赖 Jev | 服务不可用则精排失效 | 已有降级代理；生产应保留 |
| 候选超上下文 | 候选择过多超出 64K | 分批并发；控制 `RECALL_K` |
| 规模增长 | N 上千后内存索引吃力 | 届时接入持久化向量库（见 §5） |

## 附：一句话总结

> **技能是文件，索引是派生数据，召回用检索（零训练），精排用 Jev（只判断），排序与阈值用代码。**
> 全链路不需要训练任何模型——**建模的是厂商，检索的是算法，判断的是 Jev，拍板的是你的代码。**
